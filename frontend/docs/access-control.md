# Разрешения интерфейса

Первый подключённый раздел — «Ролі та дозволи». Остальные разделы пока не проверяют CASL.

`GET /auth/permissions` требует действующий bearer-токен и возвращает
`{ "permissions": ["roles.view", "roles.update"] }`. Источник — AuthContext,
который AuthGuard строит из разрешений всех ролей пользователя в БД.
Роль с именем admin сама по себе не даёт дополнительных прав.

| Разрешение       | Интерфейс                            |
| ---------------- | ------------------------------------ |
| roles.view       | Пункт меню, маршрут и список ролей   |
| permissions.view | Панель разрешений                    |
| roles.create     | Форма создания роли                  |
| roles.update     | Редактирование названия и разрешений |
| roles.delete     | Удаление несистемной роли            |

Системную роль нельзя удалить даже с roles.delete. Сервер проверяет это отдельно.
Существующий PATCH роли требует roles.update, включая изменение назначенных разрешений.
Форма хранит разрешения в исходном формате backend: `{ roles: ["view"] }`.
Включение галочки добавляет действие в массив модуля, выключение удаляет его.
Только при отправке PATCH слой API преобразует структуру в список slug, требуемый сервером.
Если permissions.view отсутствует, таблица скрыта, а массив сохраняет загруженные значения.

CASL получает module.action как can(action, module). Неизвестные действия и модули игнорируются.
Новые разделы нужно явно добавить в типы и проверки после согласования серверного контракта.

Права не хранятся в localStorage. React Query разделяет кеш по authSessionId,
обновляет права каждые 30 секунд, при фокусе окна и после редактирования/удаления роли.
До первой загрузки и при ошибке проверки доступ закрыт. Возможна задержка появления
изменений от другого администратора до следующей синхронизации; серверные guards
проверяют актуальные разрешения на каждом запросе независимо от интерфейса.

Проверка правил CASL: `node tests/ability.test.ts` из frontend (Node.js 24).
После добавления endpoint нужно перезапустить backend, если он запущен без watch.

Именованные разрешения определяются в `modules/access/model/access.constants.ts`.
Типы в `access.types.ts` выводятся из констант. В компонентах используются
`canAccess(ACCESS_PERMISSION.UPDATE_ROLES)` и
`<AccessBoundary permission={ACCESS_PERMISSION.VIEW_ROLES}>`.
Для нового ресурса добавьте его в `ACCESS_SUBJECT`, затем определите нужные пары
в `ACCESS_PERMISSION` и подключите проверку в интерфейсе. Списки для проверки
серверных строк автоматически выводятся из констант действий и ресурсов.

Таблица строится по фиксированному списку модулей `ACCESS_SUBJECT` (сейчас roles и permissions).
Каждый модуль всегда имеет четыре чекбокса из `ACCESS_ACTION`.
Чекбокс отмечен, только если массив соответствующего модуля содержит действие.
Справочник `/admin/permissions` для построения таблицы не запрашивается.

Состояние выбора роли и редактора находится в `model/useRolesStore.ts` (Zustand):
поиск, выбранная роль, разрешения, действия редактирования и статус записи.
Поля названия и slug, проверка и отправка обеих форм управляются Formik.
Таблица и чекбоксы подписываются на нужные поля напрямую, без передачи черновика через props.
При смене роли черновик сбрасывается; повторная загрузка той же роли его не перезаписывает.
Запросы и операции QueryClient остаются в `api/roleMutationOptions.ts`.
Проверка стора: `node tests/roles-store.test.ts` из frontend.

Проверки навигации выполняются в слое `app`:
`app/config/adminNavigation.ts` связывает пункты меню с разрешениями,
`AdminLayout` фильтрует пункты, а `AdminSidebar` получает готовый список без зависимости от access.
`AccessBoundary` расположен в `app/router` и используется при сборке маршрутов,
не экспортируется модулем доступа и не подключается внутри обычных страниц.
