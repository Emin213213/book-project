# Архитектурные правила Book App

## Назначение

Этот файл — обязательный чеклист для разработки и ревью архитектуры Book App. В будущих разборах
нарушения называются в формате `Архитектура §N` с объяснением причины до предложения исправления.

Правила дополняют корневой `AGENTS.md`. При конфликте приоритет имеет `AGENTS.md`, затем прямая
просьба пользователя, затем этот документ.

## §1. Разрешённые слои

В `src` используются четыре архитектурных слоя:

```text
app → pages → modules → shared
```

- `app` запускает и конфигурирует приложение;
- `pages` представляет маршруты и собирает пользовательские сценарии;
- `modules` содержит бизнес-домены;
- `shared` содержит переиспользуемый код без привязки к бизнес-домену.

Не добавлять `features`, `widgets`, `entities`, `processes` или новый слой без отдельного
архитектурного решения.

## §2. Направление зависимостей

Слой может импортировать только нижележащие слои:

- `app` → `pages`, `modules`, `shared`;
- `pages` → `modules`, `shared`;
- `modules` → `shared`;
- `shared` → только `shared` и внешние пакеты.

Обратный импорт запрещён. Например, `modules` не импортирует `pages`, а `shared` не импортирует
`modules`.

## §3. Изоляция слайсов

Слайсы одного слоя не импортируют друг друга:

- `modules/book` не импортирует `modules/cart`;
- `pages/checkout` не импортирует `pages/cart`.

Несколько модулей связываются на уровне страницы или `app`. Постоянная потребность модулей друг в
друге означает, что их границы нужно пересмотреть.

## §4. Ответственность App

В `app` разрешены:

- точка сборки приложения;
- router и таблица маршрутов;
- layouts маршрутов;
- глобальные providers;
- глобальные стили;
- глобальная конфигурация запуска.

В `app` запрещены доменные типы, Zustand stores, API конкретного домена и бизнес-правила.

## §5. Ответственность Pages

Один page-слайс соответствует странице или самостоятельной части вложенного маршрута. Страница:

- получает route params и query params;
- собирает UI из одного или нескольких модулей;
- координирует межмодульный сценарий;
- обрабатывает навигацию, связанную с этим маршрутом.

Страница не должна становиться хранилищем переиспользуемой бизнес-логики. Повторяемая логика одного
домена переносится в соответствующий `module`; бизнес-независимая логика — в `shared`.

## §6. Ответственность Modules

Каждый `modules/<slice>` соответствует одному бизнес-домену и использует термин предметной области:
`book`, `order`, `user`, а не `forms`, `data` или `helpers`.

Модуль может содержать:

- `api` — получение и преобразование внешних данных;
- `model` — типы, store, состояние и бизнес-правила;
- `ui` — доменные UI-компоненты;
- `lib` — внутренние вспомогательные функции;
- `config` — конфигурацию конкретного модуля при реальной необходимости.

Сегмент создаётся только при наличии содержимого. Пустые папки и абстракции «на будущее» запрещены.

## §7. Ответственность Shared

В `shared` находится код, который:

- не знает бизнес-терминов приложения;
- потенциально применим в нескольких несвязанных доменах;
- не управляет бизнес-состоянием.

Разрешённые сегменты: `ui`, `lib`, `config`, `api`, `assets`. Нельзя переносить код в `shared` только
ради обхода правил импортов. Если у кода один доменный потребитель, по умолчанию он остаётся рядом с
этим потребителем.

## §8. Публичный API

Каждый page- и module-слайс предоставляет внешний API через `index.ts`.

- извне импортируют только из корня слайса;
- экспортируется минимально необходимый контракт;
- внутренние файлы не реэкспортируются автоматически;
- внутри слайса используются прямые относительные импорты;
- внутренний код не импортирует собственный `index.ts`;
- `export *` не используется без обоснования.

Глубокий внешний импорт вроде `modules/book/model/useBooksStore` является нарушением.

## §9. Владение типами и данными

Доменный тип хранится в `model` владеющего им модуля. JSON-заглушка и DTO находятся в `api` этого
же модуля. Общий каталог `types` или `data` запрещён.

Если тип используется несколькими доменами, это не делает его автоматически shared-типом. Сначала
нужно определить владельца и оставить потребителям минимальный контракт. В `shared` разрешены только
действительно бизнес-независимые типы.

## §10. Межмодульные сценарии

Сценарий, использующий несколько модулей, координируется страницей:

```text
page → module A
     → module B
     → module C
```

Запрещено превращать один модуль в неявный orchestration-слой. Модулю передаются примитивы,
структурные данные или callbacks, если ему нужна реакция другого домена.

## §11. UI и стили

- бизнес-независимый UI хранится в `shared/ui`;
- доменный UI хранится в `modules/<slice>/ui`;
- компонент маршрута хранится в `pages/<slice>/ui`;
- CSS Module лежит рядом со своим компонентом;
- компонент не переносится в `shared` только потому, что используется дважды внутри одного домена.

Расположение определяется знанием компонента, а не его визуальным размером.

## §12. Именование директорий

- слои и слайсы: `kebab-case`;
- сегменты: стандартные короткие имена `ui`, `model`, `api`, `lib`, `config`;
- имя слайса выражает домен или маршрут;
- запрещены неопределённые имена `common`, `misc`, `helpers`, `utils`, `data`, `components` на уровне
  архитектурных слайсов.

Допустимы конкретные файлы внутри сегмента, например `shared/lib/date` или
`modules/book/lib/price`.

## §13. Импорты

- внешние пакеты импортируются перед внутренними модулями;
- типы импортируются через `import type`;
- путь не должен пересекать границу слайса в обход публичного API;
- циклические зависимости запрещены;
- временный legacy-импорт допускается только во время миграции и должен быть удалён в рамках
  зафиксированного этапа.

Path alias можно вводить отдельно. Он улучшает читаемость пути, но не меняет разрешённое направление
зависимостей.

## §14. Изменение архитектуры

Новый слой, новый сегмент или исключение из направления зависимостей вводится только после ответа
на вопросы:

1. Какая конкретная проблема уже существует?
2. Почему текущие четыре слоя её не решают?
3. Кто владеет новым кодом?
4. Как будет проверяться направление зависимостей?
5. Можно ли решить проблему локальной композицией проще?

Архитектура не усложняется для гипотетического будущего использования.

## §15. Правило миграции

Миграция выполняется вертикальными срезами: типы, API, store, UI и lib одного домена переносятся
вместе. После каждого среза приложение должно собираться.

Move-only и изменение поведения разделяются. Во время архитектурного переноса нельзя одновременно
заменять state manager, формат данных или UI без отдельной задачи.

## §16. Проверка перед завершением задачи

Перед завершением архитектурной задачи проверить:

- [ ] файл находится на слое, соответствующем его ответственности;
- [ ] зависимость направлена только вниз;
- [ ] отсутствуют импорты между слайсами одного слоя;
- [ ] внешние импорты используют публичный API;
- [ ] доменные типы и данные имеют владельца;
- [ ] `shared` не содержит бизнес-логику;
- [ ] не созданы пустые сегменты и преждевременные абстракции;
- [ ] CSS расположен рядом с компонентом;
- [ ] серверное состояние хранится в React Query, клиентское — в Zustand или локальном React state;
- [ ] старый файл удалён после успешного переноса;
- [ ] build и lint не получили новых ошибок.

## §17. Клиентское и серверное состояние

Серверное и клиентское состояние хранятся раздельно.

### Серверное состояние

Данные считаются серверными, если их источником истины является backend:

- книги, пользователи, заказы и другие API-ресурсы;
- результаты поиска, фильтрации и пагинации backend;
- состояние загрузки и ошибки HTTP-запроса;
- кеш полученных ответов;
- актуализация данных после добавления, изменения или удаления ресурса.

Серверное состояние управляется через TanStack React Query:

- `useQuery` — получение данных;
- `useMutation` — изменение данных;
- `queryKey` — идентификация кеша;
- `invalidateQueries` или `setQueryData` — синхронизация кеша после mutation;
- `isPending`, `isFetching`, `isError` — состояние запроса.

Запрещено копировать результат query в Zustand или локальный `useState` без отдельной причины:

```ts
// Нарушение: второй кеш серверных данных.
const { data } = useBooksQuery();
const setBooks = useBooksStore(state => state.setBooks);

useEffect(() => {
  setBooks(data ?? []);
}, [data, setBooks]);
```

Также запрещено создавать в Zustand собственные `loading`, `error`, `fetchBooks` и аналогичные поля
для HTTP-ресурсов, которыми уже управляет React Query.

### Клиентское состояние

Zustand используется только для состояния, источником истины которого является интерфейс или
браузер:

- содержимое локальной корзины до отправки заказа;
- локальное избранное, если оно не хранится на backend;
- открытие modal/sidebar;
- выбранная тема и пользовательские настройки интерфейса;
- локальные подписки или черновики, пока они не стали API-ресурсом;
- состояние, которое должно совместно использоваться несвязанными React-компонентами.

Локальное состояние одного компонента хранится в `useState` или `useReducer`, а не в Zustand.

### Правило выбора

Перед созданием store нужно ответить на вопрос: «Где находится источник истины?»

- backend или внешний API → React Query;
- браузер и несколько компонентов → Zustand;
- один компонент → `useState` / `useReducer`;
- URL, route params или query params → React Router.

Один набор данных не должен одновременно кешироваться в React Query и Zustand. Исключение требует
явного архитектурного обоснования в комментарии или спецификации.

Пример нарушения при ревью:

```text
Архитектура §17: список книг получен с backend, но повторно хранится в Zustand вместе с loading.
Источник истины раздвоен; данные и состояние запроса нужно оставить в React Query.
```

## §18. Назначение сегментов слайса

Сегмент определяется техническим назначением кода, а не типом файла. Разрешены следующие
стандартизированные сегменты:

- `ui` — компоненты отображения, UI-форматтеры и стили;
- `api` — взаимодействие с backend: функции HTTP-запросов, React Query query/mutation-хуки,
  транспортные DTO, response-типы и мапперы внешних данных;
- `model` — доменная модель: бизнес-типы, схемы, клиентские stores и бизнес-логика;
- `lib` — внутренний библиотечный код, необходимый другим сегментам этого слайса;
- `config` — конфигурация и feature flags конкретного слайса.

React Query-хуки запрещено размещать в `model`: источник их данных находится на backend, поэтому
они принадлежат `api`. DTO и форма HTTP-ответа также принадлежат `api`; доменный тип, не зависящий
от транспортного формата, принадлежит `model`.

Сегмент не создаётся, пока для него нет реального содержимого. Нестандартное имя сегмента требует
отдельного архитектурного решения.

Пример нарушения при ревью:

```text
Архитектура §18: useBooksQuery расположен в model, но управляет запросом и кешем backend-данных.
Перенести query-хук в api; в model оставить только доменную модель и клиентскую бизнес-логику.
```

## Формат архитектурного ревью

Каждое найденное нарушение сначала описывается так:

```text
Архитектура §3: modules/cart импортирует modules/book, поэтому два слайса одного слоя сцеплены.
```

Только после этого предлагается исправление. Если нарушений нет, явно указывается, какие границы
были проверены.
